# 旧纠错锁入口补充方案可行性与兼容审查

审查方式：执行者在性能剖析及原代码对照后进行方案自审；此记录不代替开发后的独立代码审查。用户已授权先补方案/兼容审查，通过后开发。

## 证据与范围

原完整容量剖析153.32秒，Go CPU样本21.33秒；系统调用和调度等待为主。每证据事务入口实际存在设置超时、admin、content、knowledge四次顺序往返。项目现有correctionSystemEnter使用MATERIALIZED生产者依赖实现同类顺序，标准PostgreSQL17与现有pgx支持，不新增依赖。

临时造数流水线/批量试验未体现收益，不纳入分支；Go JSON编码也未体现为主要热点。learning_seal_dependencies虽有规划开销，但原定义读取unit_versions/unit_asset_bindings，不能把它当作纯计算随意改为IMMUTABLE；本方案不修改原SQL函数或迁移。

## 审查结果

| 风险或兼容点 | 决策及验证门禁 |
| --- | --- |
| CTE文本顺序不保证锁获取顺序 | 每层MATERIALIZED并从前层读取，最终消费knowledge层；真实阻塞时检查已持有/尚未取得的锁 |
| 同一语句模式快照可能早于knowledge等待 | 模式读取维持后续独立SQL；等待期间完成managed激活后必须ErrRetired |
| 租约账本不应新增content锁 | false分支保持原knowledge单锁与原设置；占admin/content排他锁时仍完成 |
| 取消/锁超时产生部分持锁 | 原事务回滚及错误传播保留；控制连接重新取得排他锁证明释放 |
| 原schema/权限/评分被性能缓存弱化 | 不缓存任何数据库结论，不触碰原mode/schema查询、证据事务、评价、幂等或数据格式 |
| 性能结果仅是猜测 | 一次往返由真实驱动计数确认；全部原规模用例及同HEAD CI证明收益，不放宽预算 |

方案已说明准确文件、旧/新数据流、失败行为与原验证入口；无接口、schema、库版本或部署耦合缺口，无设计阻塞。实际锁顺序/新快照/回滚与收益仍需开发后的真实用例验证，未预先声明通过。

## 首轮实测后的范围复核

真实驱动断言观察原4次Exec失败，修改后1次通过；有序锁、等待后激活快照、false分支和取消/超时释放及原激活/租约竞争回归通过。原完整容量仍保留1000案件、10000证据、200批与全部通知页，当前153.32→147.13秒，约4.0%改善，低于初步约10%预估。

复核决策：先维持已验证的最小锁入口改动，在不变的原5分钟CI上验证实际余量，不为预估值引入额外事务、缓存或旧函数风险；若CI仍不足，再补具体热点与兼容设计。10%为初轮收益预估，5分钟、全部断言/规模与最新HEAD的CI为硬门禁，未降低验收要求。代价是仍可能需要下一轮定位，当前不宣称远端通过。
