## 1. 目标、范围与取舍

本项目面向从零基础到学术前沿的数学学习者。用户确定的优先级是内容正确性、数据数量与覆盖、学习路径、页面美观；界面以英文为主，保留中文数学术语对照，文档使用中文。

P3b 建立“原创编写或导入 → 固定版本送审 → 另一位复核者批准 → 管理员发布 → 必要时撤回”的可信内容生产流程。首条小路线从数的认识、四则运算和分数中选取，验收以完整流程和内容质量为准。P6 的至少 30 个知识点、20 个模板、300 个实例仍是后续首批内容验收指标。

| 路径 | 收益 | 成本与决定 |
| --- | --- | --- |
| 先完成小批次的完整审核发布流程 | 尽早验证数学内容、权限与发布事务，接着支持 P4 联调 | 本次采用；后台覆盖必要的编写、预览、送审、复核、发布和撤回 |
| 同时建设完整 CMS 和大规模资料转换 | 更早提供协作、批量运营及多媒体能力 | 多人协作、富文本编辑器、版本合并、大规模自动转换和视频工作流会扩大状态与权限范围，分后续需求设计 |

本阶段交付知识点、学习单元、路线和原创 SVG 的管理流程。题型模板、判分、检测、个人解锁、学习进度与回顾记录由 P4 提供；版本化反馈、证据重评和站内通知由 P5 提供。P3b 的撤回记录与事务约束为后续纠错保留接口，本阶段不产生学习资格或题目数据。

Knowledge_JSON 持续更新。采用已有离线快照工具冻结批次，保留原路径、摘要和映射，再编写正式内容包。网站运行时只使用 PostgreSQL 中的正式数据；资料中的指令、AI 审查标签、收藏状态均不作为命令、审核批准或发布资格。原文件消失不自动撤回内容。

## 2. 已有能力与必须补齐的边界

已有能力：

- P1 的 schemaVersion=1 内容包、目录、结构检查、SVG 白名单、不可变版本、导入导出及发布快照读取。
- P2 的英文知识地图和阅读页面、受限 Markdown/KaTeX、摘要绑定的公开 SVG 与响应校验。
- P3a 的稳定用户 ID、角色、会话、CSRF、凭据撤销、事务权限检查及管理员重新验证。

需要补齐：

1. 既有 knowledge_versions、unit_versions、path_versions 和 imported_packages 是不可变记录，不能拿它们做可变编辑工作区。
2. 既有 ValidateAndSeal 把内容不完整和待人工复核混在 REVIEW_REQUIRED 中。发布不能靠清空 ReviewItems 或一个客户端 approved 字段绕过要求。
3. ImportDraft 自己开启事务；送审需要在同一事务中保存不可变包、作者和送审事件，需要提取内部事务写入函数。
4. 现有私有账户接口限制 8 KiB、4 秒，不能直接承担正文和素材导入。新增内容路由使用独立限制，保留账户边界。
5. publication_members 可以表达一个快照中每个稳定 ID 的一个固定版本；替换知识版本时，依赖它的单元、路线与前置引用必须一起核验。

## 3. 架构与模块职责

~~~mermaid
flowchart TD
    Source[Knowledge_JSON 固定批次] --> Map[离线去重、来源映射与原创编写]
    Map --> Editor[Next.js 英文编辑与安全预览]
    Editor --> Private[固定内容私有代理：会话、Origin 与 CSRF]
    Reviewer[Next.js 独立复核工作台] --> Private
    Admin[Next.js 发布与撤回管理] --> Private
    Private --> HTTP[Go 内容 HTTP 边界]
    HTTP --> Workflow[publication：草稿、送审、复核及发布服务]
    Workflow --> Machine[content：结构、完整性、素材与图校验]
    Workflow --> Store[store：权限、锁、版本和事务]
    Accounts[auth：会话证明与角色类型] --> Workflow
    Accounts --> Store
    Store --> DB[(PostgreSQL)]
    DB --> Reader[既有发布快照查询]
    Reader --> Public[既有英文知识地图与阅读页面]
~~~

- publication 定义业务 DTO、状态规则及仓储接口，依赖 auth、content 和 catalogue 类型，不导入 store。
- content 校验器负责可重复的机器检查，不判断操作者角色或人工复核是否成立。
- store 实现业务仓储，在数据库事务中检查权限并读写所有相关表。
- HTTP 层处理精确路由、输入上限、Cookie、Origin、错误和请求编号；main 组装服务。
- Next.js 内容代理、客户端和运行时响应 Schema 独立于现有账户 DTO。共享 Cookie 选择和严格编码检查时采用明确参数，账户原有限制保持原值。
- PostgreSQL 保存运行时内容、版本、审核、来源映射和发布指针。JSON 内容包仍用于离线审查及导入导出。

## 4. 权限、责任与可见范围

| 角色 | 本阶段能力 |
| --- | --- |
| learner / 匿名 | 继续浏览有效已发布内容；不能读取草稿或执行内容管理操作 |
| editor | 创建自己的工作区，编辑、导入、预览、送审和创建修订；查看自己的送审与复核意见 |
| reviewer | 查看已冻结的送审内容，完成独立复核；不能以此角色修改作者草稿 |
| admin | 查看内容工作流及审计，准备和激活发布快照、撤回版本；不自动拥有 editor 或 reviewer 的写入能力 |

一个工作区只有一个可编辑的负责人。本阶段不做实时协作、转移所有权或合并不同作者的修改。多角色账户执行不同动作时仍分别校验角色。

作者集合由服务器记录，至少包含工作区负责人；修订继承所依据送审的作者集合，同一不可变成员版本的已有作者记录也会并入。客户端不能删改作者集合，复制或换工作区不能让作者取得自审资格。既有 CLI 草稿缺少平台作者时，编辑者通过明确的“认领为待复核草稿”操作承担整理责任，标记 legacyUnattributed，并留下来源与认领说明；不会继承批准状态。

审核批准要求复核者不在该送审作者集合中。系统可证明不同账户，人员独立性仍由管理员授予 reviewer 时人工核对，并由复核者在批准时填写核验说明。原始参考书作者不自动成为平台账户作者；平台作者集合描述本次整理与编写责任。

所有私有内容操作检查有效会话、凭据版本、当前角色和 mustChangePassword。写操作同时校验 CSRF；发布激活与撤回要求管理员在最近 5 分钟内重新验证密码。用户 ID、角色或批准字段不能由请求体指定为可信身份。

未经登录返回 401，缺少动作角色返回 403；具有动作角色但无权访问某个工作区时返回 404，避免泄露其存在。权限和数据库不可用是不同状态，页面不能把故障显示成匿名或成功。

## 5. 草稿、送审与复核状态

### 5.1 可编辑工作区

工作区保存 schemaVersion=1 包、固定目录版本、私有来源映射和 SVG 字节。正文采用结构化表单：知识点类型、英文与中文标题、陈述、适用范围、目标、条件、体系、证明、来源、关系；单元包含讲解角度、例题、反例及素材；路线包含固定版本节点。提供 JSON 文件导入和导出，受限 Markdown 编辑与安全预览复用 P2 组件。

工作区状态为 editing 或 submitted。固定校验摘要是服务器生成的带用途标识 SHA-256，覆盖目录、包、精确素材摘要、sourceMap、工作区 revision 和作者责任；同一输入有确定结果，不由浏览器声明可信摘要。送审复制 sourceMap 和作者集合，并保存独立 frozenDigest，复核与 manifest 绑定 frozenDigest。工作区之后的变更不能改变冻结来源或作者，新增关联行也不得使其与冻结摘要不一致。editing 可以保存结构合法但尚不完整的内容；缺失目标引用等业务问题显示在检查报告中。非法 JSON、字段、编码、NUL、危险标记或不合法 SVG 不能保存。可编辑与可送审分别显示，防止把“保存成功”理解为可发布。

每次保存携带 expectedRevision，服务器比较当前递增 revision。冲突返回 409 DRAFT_CONFLICT，保留浏览器尚未保存的输入，提示重新读取；不自动覆盖其他标签页的修改。包与版本号必须显式展示。编辑历史保留动作、前后摘要和修订号，送审前的每次正文变化不要求永久保存全文副本。

已有 CLI 包可以认领；已有送审的负责人可以创建自己的修订工作区；其他编辑者需要通过既有不可变包的显式认领建立自己的整理责任。复制只复制内容与来源，清除审批状态，继承可追溯作者责任。发生正文变化时，对应知识点、单元或路线的同 ID 不可变成员必须使用新版本，包本身也使用新版本。素材本身没有递增 version 字段，使用新 SHA-256；改变素材字节或数学含义时，其所属知识点和引用该素材的单元必须创建新版本并重新复核，既有素材 member 的 version=1 保持。版本冲突由服务器拒绝，不暗改版本号。

### 5.2 固定版本送审

送审携带 expectedRevision 和本次校验摘要。事务中重新读取工作区，运行机器完整性检查，用数据库中的素材字节校验并封存。通过后把正式包写入既有不可变表，同时插入送审及作者、成员关联和审计，将工作区设为 submitted。

任何失败均回滚，不保留半个正式包或已提交状态。工作区冻结后不能原地修改；复核退回后可重新编辑，原送审仍保留。批准后修订需要创建新工作区，批准不会跟随修订继承。

送审状态为 pending、approved 或 returned，只允许 pending 到两个终态。退回决定在同一事务中使其原工作区恢复 editing，工作区 revision 递增，原冻结内容及退回记录保留。一个送审只有一个最终复核决定；并发复核中第一笔合法事务完成，另一笔返回 409 REVIEW_CONFLICT。请求幂等重放同一成功决定时返回原结果。

### 5.3 独立数学复核

复核页面展示冻结的包版本、目录摘要、素材摘要、作者、来源映射、机器报告和安全预览，禁止编辑冻结正文。批准按整份送审批次进行，覆盖其中所有知识点、单元、路线与素材；不能批准其中一节后把整包视为通过。

批准记录包含：

- 数学陈述、条件、体系与证明核对。
- 讲解、例题、反例及多个讲解角度核对。
- 前置关系、固定版本引用与路线顺序核对。
- 来源、使用条件、署名及原创素材核对。
- 图形与数学内容的一致性核对；没有图形时仍明确记录已检查其适用性。
- 独立性说明与复核意见，各为 10—1000 个 Unicode 码点、最多 3000 个 UTF-8 字节，不含 NUL；该双重限制确保两段文字与检查项能进入 8 KiB 控制请求。

上述检查项均需明确完成，不能使用 AI 审查标签代替。退回必须填写具体理由。人工批准只解决数学、表达和使用条件判断；机器完整性问题必须先通过。批准后复核者失去 reviewer 角色，不自动撤回已发布内容；尚未激活的内容可以通过另建送审取得新的独立批准，或在原复核者恢复角色后重新校验原批准的当前资格，不能修改原最终决定。

## 6. 机器校验与发布准备条件

保留离线 ValidateAndSeal / content-check 的现有报告兼容性：草稿仍显示待复核。内部提取可接收素材读取器的共同结构检查，文件读取器保持现有防越界与防符号链接规则，数据库/内存读取器按 asset ID 绑定精确字节，忽略 path 的磁盘含义，但仍校验其相对 SVG 路径格式。

新增工作流检查报告分三类：

| 类别 | 示例 | 送审 / 发布行为 |
| --- | --- | --- |
| structuralErrors | 非法引用、重复 ID、前置循环、危险 Markdown、摘要不符、素材归属或版本绑定错误 | 阻止送审和发布 |
| completenessErrors | 缺少陈述、适用范围、学习目标、证明、来源、正文讲解或例题 | 阻止送审和发布；允许安全草稿保留 |
| humanReviewRequirements | 结论与证明正确性、教学质量、来源使用条件及独立性 | 固定送审获得独立批准后满足，不能由机器默认置为完成 |

完整性门槛：

1. 送审包至少包含一个知识点；每个知识点有非空英文标题、中文术语、陈述、适用范围、至少一个学习目标、明确体系和至少一个来源；条件可为空，但复核必须核对是否确实无需额外条件。
2. theorem 必须有非空证明；axiom 明确所属体系；其他类型的 proof 可为空，不能因此伪造证明已获机器验证。
3. 每个知识点至少有一个对应学习单元；每个单元有至少两种不同 kind 的非空讲解角度及至少一个例题。反例在数学上适用时由复核者要求补齐，不为了数量虚构反例。
4. 来源有作者、标题、使用条件及署名信息；纯原创陈述允许 original 类型 URL 和 accessedAt 为空，作者和许可仍须明确；external 必须指向可公开的 HTTPS 原始出处，包含合法 YYYY-MM-DD 获取日期。内部 Library / 本地批次位置只进入私有来源映射。
5. 素材由项目自行制作，作者、许可及署名信息完整；仅接受已有受限 SVG 白名单，SHA-256 与实际字节一致。不引入新的图片或视频格式。
6. 送审包保持现有完整引用闭包，路线包含所有节点的前置，并遵守节点的前置先于后继的顺序。

完整性检查只是明确的最低条件，不能证明数学正确性。骨架通过 P1 导入不代表可以送审。本次不修改既有 schemaVersion 或历史包摘要。

## 7. 发布快照与激活

### 7.1 准备候选快照

管理员选择 1—20 个 approved 送审，提交 expectedHead（首次为 null）和发布说明。候选是“当前快照 + 选定的完整送审批次”的固定集合，每个 kind / ID 只有一个版本。

合并规则：

- 不同送审对同一 kind / ID 选择不同版本或字节时返回 VERSION_CONFLICT；不能按数组顺序静默覆盖。
- 新知识版本替换当前同 ID 知识；属于被替换旧知识版本的单元和素材从候选中移除，差异报告明确列出。
- 其余既有成员保留，新送审成员按 ID 替换对应成员。保留的知识点和路线如果仍引用旧前置版本，整个准备失败，要求提交包含必要依赖更新的已审核版本。
- 单元引用的 asset ID 和摘要必须符合既有 unit_asset_bindings；更换素材不能把旧单元暗中绑定到新字节。
- 新增的所有成员都必须来自选择的已批准送审。旧快照成员可以继承其先前发布依据，不能从任意 CLI 草稿补缺口。

整体检查固定目录版本、前置闭包与循环、路线顺序与闭包、讲解完整性、来源、素材绑定、撤回黑名单以及所有新增内容的审核依据。全量快照中的 related / derivation 目标已经不可用时沿用 P1 查询行为：不展示该非前置边；不能当作有效前置或修改原版本。新送审自身仍须满足完整包引用检查。

首版只支持同一 catalogueVersion 合并。跨目录版本迁移需要后续独立兼容性设计，本阶段不能自动切换目录以规避审核。

成功时插入 draft 状态的 publication_snapshots、完整 publication_members 和不可变 manifest，返回快照 ID、baseHead、manifestSHA、新增/替换/移除数量与确切差异。准备不会改变公开查询结果。manifest 绑定每个成员的包、版本、内容摘要、素材绑定以及新增成员的送审和批准事件。

### 7.2 原子激活

激活请求携带 snapshotId、expectedHead、expectedManifestSHA、reason 和幂等键。事务中：

1. 检查当前管理员会话、CSRF、角色、最近重新验证。
2. 验证 manifest、成员与固定字节一致，新增批准仍有效，复核者当前拥有 reviewer 且不属于作者集合。
3. 检查当前 head 与候选 baseHead 及请求 expectedHead 完全一致；检查新的撤回记录，重新校验整图。
4. 将该快照从 draft 单向变为 published，更新 singleton head，写入激活事件及幂等结果，一次提交。

当前 head 已变化返回 409 PUBLICATION_STALE，不按旧候选覆盖新发布或撤回。准备快照的成员与 manifest 禁止 UPDATE / DELETE，published 快照的状态和目录禁止再修改；旧 head 指向过的 published 快照继续保留。

公开读取继续以既有 head 和 repeatable-read 事务取内容。激活提交前已开始的读取可能完成旧快照，提交后新开始的读取使用新 head；不存在一个请求混合新旧版本。继续 no-store，不把已经撤回的内容缓存为有效版本。

管理员不直接编辑 publication_members，不提供“强制发布”“恢复旧 head”或略过复核接口。历史快照只用于私有审计；重新启用内容走新的校验和发布流程。

## 8. 基础撤回

撤回对象是固定知识点、单元、路线版本，或精确 SVG 字节摘要。请求必须填写理由、expectedHead 并通过管理员最近重新验证。版本记录和历史审核不可删除或改写。

同一事务写入永久版本撤回记录，基于当前 head 创建一个新的发布快照，并计算公开使用范围：

- 撤回知识点：移除该知识版本、其单元和素材；递归移除前置依赖它的知识点及所属单元、素材；移除包含这些节点的路线。
- 撤回单元：停止该单元对应知识版本及其依赖路线的公开使用。讲解与知识一起复核，本阶段采用整节点暂停的保守规则。
- 撤回 SVG 摘要：停止引用该字节的知识版本、单元及上述前置依赖和路线，不只删除页面中的一张图。
- 撤回路线：只移除该路线，仍合格的知识点继续可读。
- related / derivation 是非前置关系，继续按公开查询过滤不可用目标，不据此递归移除知识点。

撤回黑名单记录实际问题对象；依赖对象的退出记录在派生快照差异中，并非把所有依赖版本永久判为错误。空快照合法，此时目录保留、详情为现有不可用状态。对于已批准但未发布的版本，撤回也记录黑名单并生成新的 head；首次无 head 时生成空 published 快照，从而使此前准备的候选失效。

派生快照保存 beforeHead、撤回事件、移除原因及摘要，通过撤回后专用可用性校验，最后切换 head。该操作只移除既有内容，不加入未经复核的替代内容，因而不需要另做数学批准。相同版本不能直接取消撤回；需要新版本、新复核和新发布。

发布与撤回使用同一事务锁。撤回提交之后，任何旧候选都因 head 不一致或黑名单检查失败而不能恢复问题内容。

P4 在测评与授予资格时使用这一版本状态约束和同一发布锁；P5 在撤回事务内增加证据限制，再执行异步重评。本阶段只保留清晰扩展点，不创建不存在的学习表或后台重算任务。

## 9. 数据模型、幂等与并发

新增迁移 00004_content_workflow.sql；不重写 00001—00003。

| 表 | 责任与关键约束 |
| --- | --- |
| content_workspaces | UUID、owner_user_id、目录版本、包 JSONB、私有来源映射、revision、editing/submitted、base_submission_id、时间；用户和目录外键 |
| content_workspace_assets | 工作区 / asset ID 唯一、摘要和字节；每项不超过 1 MiB，工作区删除不通过产品接口提供 |
| content_submissions | 固定包外键、目录及包摘要、工作区与 revision、冻结 sourceMap/作者责任/frozenDigest、pending/approved/returned；冻结正文通过 imported_packages 引用 |
| content_submission_authors | 送审 / user ID 唯一；不可变作者责任 |
| content_submission_members | 送审与精确 package_members 的外键，成员摘要；用于继承作者与发布依据 |
| content_review_decisions | submission ID 唯一、复核 user ID、批准/退回、检查项、独立性与意见、数据库时间；不可变 |
| content_publication_manifests | snapshot ID 唯一、baseHead、规范成员与依据、SHA-256、创建管理员；不可变 |
| content_withdrawals | 固定对象身份 / 摘要唯一、原因、管理员和请求编号；永久且不可变 |
| content_workflow_events | 动作、操作者、对象、前后摘要/状态、理由、请求编号与数据库时间；不可变 |
| content_idempotency | actor / route / UUID key 唯一，请求摘要、结果身份与状态；不存请求凭据 |

作者、复核决定、manifest、撤回和工作流事件均禁止 UPDATE / DELETE。送审表的冻结字段不可修改，触发器只允许 pending 到 approved/returned 的一次状态更新，并禁止 DELETE；工作区 revision 按保存递增。新增 manifest 后该快照成员不能更改，目录不可变，状态只允许一次 draft → published。P1 产生且未关联 manifest 的旧 draft 快照保持兼容，不能通过新工作流直接激活。

幂等规则：

- 创建、保存、认领/修订、送审、决定、准备、激活及撤回写入均携带 UUID v4 Idempotency-Key。
- 同一 actor / route / key，规范请求摘要相同，返回原结果；摘要不同返回 409 IDEMPOTENCY_CONFLICT。
- 幂等检查也要校验当前有效身份和动作权限，不能凭旧结果绕过角色撤销。
- 激活或撤回重放只返回历史操作结果，不重新切换 head；页面另外读取当前状态。
- 成功结果与业务写入同一事务提交；失败与中断不留下成功记录。P3b 不自动清理这类记录，保留审计与重放能力。
- 内容导入相同版本相同字节仍幂等；同版本不同字节继续 IMMUTABLE_CONFLICT。

所有内容写入采用统一顺序；大正文和冻结内容可先做有界纯计算，但取得锁后要重新核验 revision、摘要、权限与正式版本冲突。快照校验使用已计数限额的固定数据库内容，不能把锁外预检结果直接当成激活依据：

1. 既有账户管理 advisory lock 1296127049。
2. 既有内容导入 advisory lock 1296127048。
3. 相关 auth_users 按 UUID 排序锁定，含操作者、此次批准的复核者及相关作者；然后锁操作者 auth_sessions。
4. 校验数据库时间、会话、凭据版本、CSRF、mustChangePassword 和角色；最后锁工作区、送审、head 及业务行。

复用这一顺序避免授权检查与角色撤销竞争。既有 CLI ImportDraft 只取内容锁，不再反向取得账户锁；P3a 角色变更取管理锁与用户/会话行，密码变更取用户后会话行，均不引入逆序。读取会话上下文持会话锁时不再取得用户行锁，维持现有约定。

提取 importValidatedTx，只供 store 内部调用；ImportDraft 保留原公共方法、30 秒 CLI 超时和报告语义。内容工作流调用该函数时使用自己的事务和更短截止时间，不嵌套事务。

首版将管理性内容写入串行化，成本是编辑者之间的写吞吐有限；其收益是简单、可验证的权限与版本一致性。性能回归测量后再决定是否细分锁，本次不提前拆成多个互相独立的发布事务。

## 10. 私有接口与输入边界

统一前缀为 /api/v1/content，根路径及未知路由返回 404；固定方法，不允许任意上游 URL 或路径。公开 /knowledge、/paths、/assets 契约不变。

| 方法与相对路径 | 请求 / 响应要点 |
| --- | --- |
| GET /drafts | 仅本人草稿；admin 可按允许的筛选查看；分页摘要不含正文或 SVG 字节 |
| POST /drafts | catalogueVersion、package、assetBytes、sourceMap；创建本人工作区 |
| GET /drafts/{id} | 工作区、revision、作者责任、包、素材元数据和检查报告 |
| PUT /drafts/{id} | expectedRevision、完整替换包/素材/映射；单事务保存 |
| GET /drafts/{id}/assets/{sha256} | 仅该工作区绑定的私有 SVG |
| POST /drafts/{id}/validate | expectedRevision；返回三类检查及内容摘要 |
| POST /drafts/{id}/submit | expectedRevision、expectedDigest；返回冻结送审 |
| POST /drafts/adopt | packageId、packageVersion、认领说明；认领既有 CLI 包 |
| GET /submissions | 本人的送审、reviewer 待审列表或 admin 审计列表；角色决定服务器筛选范围 |
| GET /submissions/{id} | 冻结版本、作者、来源、机器报告及最终复核决定 |
| GET /submissions/{id}/assets/{sha256} | 仅该送审固定绑定的私有 SVG |
| POST /submissions/{id}/revision | 基于已冻结送审创建本人修订工作区，继承作者与来源 |
| POST /submissions/{id}/decision | approve/return、检查项、independenceNote、note |
| GET /publications | admin 的候选、历史激活与当前 head 摘要 |
| GET /publications/{id} | admin 的固定 manifest、审核依据和差异 |
| POST /publications/prepare | submissionIds、expectedHead、reason |
| POST /publications/{id}/activate | expectedHead、expectedManifestSHA、reason |
| POST /withdrawals/preview | target；返回绑定 currentHead 的影响成员与数量，不写入 |
| POST /withdrawals | target、expectedHead、reason；返回撤回事件及新 head |

UUID 均要求规范小写 v4，正文中的数学稳定 ID 沿用现有格式；版本在有符号 32 位正整数范围。target 是严格区分的 knowledge/unit/path {id,version} 或 asset {sha256}，不接收客户端给出的可信内容摘要。

新内容工作流采用下列固定上限：

操作说明与复核文本只在要求理由的动作中强制填写，统一为 10—1000 个 Unicode 码点且最多 3000 个 UTF-8 字节，拒绝全空白与 NUL。创建、保存和自动审计无需编造理由。缺少账户 origin 配置返回既有 AUTH_NOT_CONFIGURED；缺少内容迁移时新内容接口返回 503 CONTENT_NOT_CONFIGURED，既有账户及只读接口继续按原规则运行，不自动迁移。

- 创建 / 保存正文 envelope 最多 8 MiB；其中序列化 package 最多 2 MiB，解码 SVG 总量最多 4 MiB，每项最多 1 MiB。assetBytes 以 asset ID 和严格标准 Base64 表达，必须与包中素材一一对应。
- 每个工作区至多 100 个知识点、200 个单元、20 条路线、16 项素材。大资料按批次拆分，网页不直接上传 ZIP 或原始资料库。
- 其余控制请求最多 8 KiB；sourceMap 最多 256 KiB，只接受数据字段，保存批次摘要、相对路径、文件摘要、legacyId 和使用说明，不执行其中文本。
- 私有 JSON 响应最多 4 MiB；详情不含 Base64 字节，素材按受控私有接口读取。列表 limit 默认 20、最大 100，offset 0—100000，允许的状态筛选固定枚举，查询参数不得重复。
- 服务端和代理拒绝未知字段、大小写别名、重复键、错误 UTF-8、未配对代理项、NUL、尾随 JSON、超过 32 层嵌套、未允许的查询和非 JSON 正文。数学文本保留原始有效 Unicode，不做改变含义的自动替换。
- 固定图校验上限为一个候选快照 1000 个知识点、4000 个单元、200 条路线、16000 条知识关系和 1000 项素材。候选全部正文、路线、来源与素材元数据的规范 JSON 总量最多 32 MiB，任一按既有公开契约生成的知识或路线响应不得超过既有 10 MiB JSON 上限，唯一 SVG 字节总量最多 10 MiB；加载前先核验数据库记录的计数与字节总量，超过限额立即拒绝，不先把全部内容载入内存。超限明确返回 CONTENT_LIMIT_EXCEEDED；提高此上限需根据测量单独审查，不把已有源资料全部加入一个发布事务。

这些是新增工作流的边界；既有 CLI 正式包 10 MiB、素材总量 10 MiB 和内容 Schema 不变。过大的旧 CLI 包可继续离线导出，需要拆成满足网页上限的新整理批次后送审。

内容请求总截止 8 秒，Next.js 代理总截止 10 秒，Go 现有服务器 15 秒读写超时保持；账户接口仍为原来的 4/5 秒。正文读取计入总截止，限制 chunked 流实际累计字节，客户端断开即取消；数据库事务受剩余请求截止限制，锁等待上限 1 秒。超时显示操作结果尚未确认，保留原幂等键；用户可主动以同一 key 和完全相同请求重试，服务器返回原成功结果或完成尚未提交的操作，浏览器不自动重试写入。

复用 PostgreSQL UTC 固定窗口原子限流，但新增内容预算：有效账户每分钟读取 120、普通写入 30、送审/复核/准备/激活/撤回共享每分钟 10；全服务普通写入 120/分钟、重操作 40/分钟。每进程内容验证与大正文请求最多同时 2 个，无空位立即 429，不无限排队。角色初查、限流与容量检查在读取大正文前完成；事务内仍重新授权。这是本机首版预算，P7 按实际容量复核。

私有 SVG 代理只转发选中的会话 Cookie，限制 1 MiB、校验所请求摘要与 SVG 白名单，要求 image/svg+xml、nosniff、CSP sandbox 与 private,no-store；不转发 Set-Cookie，不能用全局摘要接口绕过工作区可见范围。JSON 响应也在完整校验后返回，不回显数据库异常、Cookie、CSRF、原始请求体或服务器路径。

错误契约沿用英文消息、稳定 code、requestId，新增 409 DRAFT_CONFLICT / REVIEW_CONFLICT / IMMUTABLE_CONFLICT / IDEMPOTENCY_CONFLICT / VERSION_CONFLICT / PUBLICATION_STALE，422 CONTENT_NOT_READY / CONTENT_INVALID / REVIEW_REQUIRED / CONTENT_LIMIT_EXCEEDED，413 PAYLOAD_TOO_LARGE，及已有 401/403/404/429/503。具体机器问题以受限 path/code 返回，最多 100 项并标明 truncated；不得把被截断报告误判为无问题。

撤回预览虽然使用 POST，只计算影响，不创建业务事件或幂等成功记录；仍要求管理员、CSRF，并计入重操作限流。真实撤回在事务内独立计算。后台版本选择来自已授权 GET /submissions/{id} 和 GET /publications/{id}，不开放任意未授权版本查询。

| 资源与请求时限 | 小批次、明确图上限、验证并发 2、8/10 秒截止；实现验证最大合法输入与并发的时间/内存，若不满足则调整方案后再实施 |
| 数学及来源正确性 | 最低完整性机器检查 + 独立人员复核；不把收藏、AI 标签或测试批准当成真实数学批准 |
| 迁移与回退 | 备份后增量迁移；真实使用后只回退应用并保留新增表，不能 down 删除审核、作者或撤回记录 |
| 账户启用 | 现有开发库不自动初始化真实管理员；测试在随机隔离数据库进行。真实启用按既有账户操作说明及备份/迁移流程执行 |
| 外部服务与部署 | 无新增付费或账号服务依赖；域名、HTTPS、服务器容量、站外备份和正式上线依然由 P7 验证 |

现有模块、版本结构、角色和查询方式可以支撑上述方案，没有必须先更换技术栈或服务的静态阻塞。请求上限与并发锁的实际性能在实现阶段测量，是发布本功能的验收条件，不宣称已测得性能。正式数学内容发布还需要不同人员的独立复核；人员未落实时技术验证可继续，真实内容保持未发布。

## 14. 验收与后续执行顺序

执行计划按以下顺序细化，避免一次建立全部状态：

1. 工作流契约、迁移、作者责任、幂等及事务授权。
2. 机器校验拆分、数据库素材校验及事务导入复用。
3. 工作区、认领、修订、固定版本送审。
4. 独立复核、并发终态及权限撤销。
5. 候选合并、manifest、整图校验与原子激活。
6. 撤回闭包、黑名单、派生快照与公开读取回归。
7. 英文管理页面、真实浏览器全流程和最终代码审查。

必验场景：

- 旧 content-check、CLI 导入导出、P2 公共读取与 P3a 账户回归通过，生成 API 类型零漂移。
- 匿名、learner、跨工作区、伪造身份、错误 CSRF、失效会话、必须改密码及角色撤销全部拒绝，草稿与私有素材不泄露。
- 重复键、大小写别名、未配对代理项、NUL、超限正文、chunked 超限、危险 SVG/Markdown、缺引用、循环、空证明、来源不足和错素材摘要被拦截。
- 版本/修订冲突和失败送审不留下部分导入；相同请求幂等，换正文复用 key 失败。
- 作者不能自审，复制不能消除作者责任，批准固定正文；两名复核者竞争只出现一个合法终态。
- 两次并发发布不能互相覆盖；发布与角色撤销、发布与撤回使用真实 PostgreSQL 同步屏障测试，不能用顺序请求代替竞争。
- 更换知识版本但未更新路线或前置失败；审核不足的 CLI 草稿无法进入发布候选。
- 撤回知识、单元、SVG 与路线的公开结果符合本设计；旧候选无法恢复撤回对象，旧快照与审计仍可追溯。
- 最大合法输入和快照边界在限定时限内完成，容量拒绝、取消和超时不泄漏校验槽位或事务。
- 1280 / 390 像素真实浏览器验证：编辑、保存冲突、送审、独立复核、准备差异、重新验证、激活、匿名读取、撤回、空状态和键盘操作；不使用假 API 成功响应。
- 一条小路线由实际独立人员完成复核后才能计为数学发布验收；随机测试数据库中的批准只验证技术流程。

开发前再次更新 master 并新建 codex/ 功能分支。Go 调试、测试和构建使用 CGO_ENABLED=0、GOTOOLCHAIN=go1.27.1；每次验证由 tools/verify/run.mjs 限制在 540 秒内，Go 单批 timeout 5m。实施后进行独立代码审查、修复必要问题、回归和 CI，通过 Git 创建 PR；不自行部署。

本文已逐项检查范围、状态转换、历史不可变性、权限与锁顺序、版本闭包、旧接口兼容性及验收边界。书面设计已确认；具体执行计划经审阅后进入实施。
